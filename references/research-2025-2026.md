## 1. Executive findings

The 2025-2026 consensus is a layered evaluation system rather than one universal score:

1. Verify the external outcome or resulting state.
2. Inspect and grade traces to localize routing, retrieval, tool, handoff, and memory failures.
3. Use deterministic assertions wherever success is computable.
4. Use task-specific LLM judges only for subjective or semantically flexible criteria, calibrated against human labels.
5. Run repeated trials and measure reliability, not one-shot success.
6. Separate capability hill-climbing from near-perfect regression protection.
7. Combine offline evals, production monitoring, A/B tests, user feedback, and periodic human review.
8. Feed real, redacted failures back into versioned datasets.

Anthropic formalizes the distinction among task, trial, grader, transcript/trace, outcome, eval harness, agent harness, and suite. This distinction matters: a convincing final response can coexist with a failed environment outcome, and a successful outcome can be reached by a valid path absent from a rigid reference trajectory.

OpenAI's current guidance similarly moves from trace grading during debugging to datasets and repeatable eval runs once “good” is defined. OpenAI's legacy Evals platform is scheduled to become read-only on 2026-10-31 and shut down on 2026-11-30, so new internal standards should remain portable and should not center on that retiring product.

## 2. Industry standard

### Eval-driven development

Write a capability test when defining a new behavior, then implement until it passes. When stable, promote the case to regression. Add a focused regression case for every confirmed incident. Run affected suites on every prompt, model, tool schema, routing, retrieval, memory, or policy change.

### Outcome-first, trace-assisted evaluation

Outcome checks answer whether the user goal was actually achieved. Trace checks answer why. OpenAI trace grading captures model calls, tools, guardrails, and handoffs. LangSmith distinguishes final-response, trajectory, and single-step evaluation. Braintrust recommends end-to-end and incremental step evaluation. Anthropic warns against taking scores at face value without reading transcripts.

### Mixed graders

Use three complementary grader classes:

- Code/executable: fast, reproducible, and strong for objective behavior.
- Model-based: scalable for semantics and flexible workflows, but biased and fallible.
- Human: highest-value calibration and discovery signal, but slower and more expensive.

OpenAI recommends pairwise or pass/fail judge tasks and explicit rubrics; it documents position and verbosity bias. Research published in 2025 reports that correlation alone is insufficient to validate judges and that even strong judges remain inconsistent on difficult cases. Therefore judge evaluation, or meta-eval, is a first-class suite.

### Production-representative data

Strong datasets combine product requirements, manually tested flows, domain-expert cases, historical bugs, production traces, synthetic boundary cases, and adversarial cases. OpenAI recommends typical, edge, and adversarial examples. Anthropic recommends balanced problem sets, reference solutions, and tasks whose pass/fail verdict two experts would independently agree on.

### Repeated trials

Agent output is stochastic and long trajectories compound errors. Report repeated trials per task. `pass@k` measures whether retries can eventually succeed; `pass^k` measures consistent reliability. Tau-bench demonstrated why this matters: one-shot task success can appear tolerable while success across repeated trials collapses.

### Continuous loop

The mature loop is:

```text
instrument -> inspect traces -> label failures -> curate dataset
-> run paired experiments -> gate changes -> deploy gradually
-> monitor production -> human review -> add regressions
```

No layer is sufficient alone. Anthropic explicitly compares the combination to a Swiss-cheese model: automated evals, production monitoring, A/B tests, feedback, transcript review, and human studies cover different gaps.

## 3. Metrics that produce engineering signal

### High-signal metrics

- Environment task success and exact state transition.
- Policy/authorization violation and forbidden action rate.
- False-success claim rate.
- Tool selection precision/recall and semantic argument accuracy.
- Retrieval recall@k, precision@k, MRR/nDCG, and evidence coverage.
- Claim-level faithfulness and citation precision/recall.
- Handoff/router precision and recall.
- Memory write/retrieval precision and isolation violations.
- Per-case pass rate, `pass@k`, and `pass^k`.
- p95/p99 latency, token use, and cost per successful task.
- Retry, timeout, loop, duplicate-side-effect, and recovery rates.
- Per-slice candidate-baseline delta with uncertainty.

### Useful but conditional metrics

- LLM-judge correctness/completeness/source-quality scores after human calibration.
- Trajectory similarity where a true path invariant exists.
- Step efficiency after task success is protected.
- User satisfaction and escalation rate with selection-bias caveats.
- Semantic similarity when equivalence to a reference is actually meaningful.

### Weak as primary release gates

- Perplexity, BLEU, ROUGE, or embedding similarity for agent success.
- A single aggregate “quality” score.
- Public leaderboard position detached from the product distribution.
- One-shot judge scores without agreement data.
- Raw number of tool calls without task and cost context.

## 4. How production teams evaluate agents

Anthropic reports several concrete patterns:

- Claude Code started with narrower concision and file-edit evals, then added behaviors such as over-engineering, alongside monitoring, A/B tests, research, and user feedback.
- Descript evaluates whether its editing agent avoids breakage, follows the request, and performs the edit well. It evolved from manual review to product-defined LLM rubrics with periodic human calibration and keeps distinct quality and regression suites.
- Bolt built an eval system using static analysis, browser agents, and LLM judges for instruction following.
- Claude for Chrome uses tool-selection evals for context-sensitive actions.
- Anthropic's research system began with about 20 representative queries, used a rubric for factuality, citation accuracy, completeness, source quality, and tool efficiency, and retained human testing for subtle source-selection bias.

Anthropic's multi-agent research results also show why architecture evaluation needs a budget baseline: its system improved internal research quality but multi-agent runs used far more tokens. The company reports that multi-agent benefit is strongest for breadth-first, parallelizable research and weaker for tightly dependent tasks. A multi-agent release decision must compare quality gain against latency and total cost, not only against its own prior version.

Braintrust describes the production cycle as playground iteration, immutable experiments, CI/CD evaluation, asynchronous production scoring, and promotion of interesting production traces back into datasets. LangSmith and Phoenix describe similar trace-to-dataset-to-experiment loops.

## 5. Common blind spots

The failures most often missing from initial eval suites are:

- Agent says an action succeeded, but the database/API/file state did not change.
- Action was applied twice after a retry or timeout.
- Tool name is correct but arguments are semantically wrong, stale, or cross-tenant.
- Agent should not call a tool, search, hand off, or remember, but does.
- Tool returns malformed, partial, delayed, duplicated, or contradictory data.
- Authorization or policy checks happen after an irreversible action.
- RAG retrieves the right document but misses the evidence span; or the answer hallucinates despite having evidence.
- Corpus deletion, freshness, ACL, multilingual, and metadata-filter behavior.
- Long conversations lose state after compaction or mix state between users.
- Memory stores transient, sensitive, contradicted, or irrelevant facts and later over-trusts them.
- Router works one way but fails when the topic changes mid-session.
- Multi-agent systems duplicate work, loop in handoffs, lose subagent evidence, or create conflicting writes.
- One subagent fails and the supervisor silently presents an incomplete result as complete.
- Latency/cost averages hide pathological long-tail loops.
- Environment flakiness is misclassified as model regression.
- Judge prompt injection, position bias, verbosity bias, self-preference, or rubric drift.
- Evaluation task is ambiguous, unsolvable, or has a buggy reference test.
- Capability suite saturates and becomes unable to distinguish improvements.
- Public benchmark contamination or agent awareness of benchmark artifacts.
- Optimization overfits the visible eval and degrades unseen production slices.

## 6. Tool landscape

Tool popularity changes quickly; choose by fit and existing stack, not a universal ranking.
There is no authoritative neutral census of production usage across all vendors. The most commonly encountered choices in current public engineering ecosystems are LangSmith for LangChain/LangGraph teams, Braintrust for managed vendor-neutral experiments, DeepEval for Python/pytest workflows, Promptfoo for local matrices and red teaming, Ragas for RAG metrics, and Phoenix/OpenInference for open-source observability. OpenEvals is a newer evaluator library rather than a complete observability platform. Treat this as a practical market map, not a measured market-share ranking.

### OpenAI

Current OpenAI agent tooling supports trace grading, datasets, graders, and agent workflow evals. It is a strong choice for teams already using the Agents SDK and OpenAI tracing. The legacy Evals product deprecation makes a portable internal case/result format essential. OpenAI graders support string checks, text similarity, model scoring, and Python execution; its best-practice guidance emphasizes continuous, task-specific evals and human calibration.

### Anthropic

Anthropic's strongest public contribution is methodology rather than a general vendor-neutral eval platform: outcome/transcript distinction, multiple trials, balanced tasks, reference solutions, capability versus regression suites, mixed graders, transcript inspection, and a holistic monitoring loop. These practices are framework-independent.

### LangSmith and OpenEvals

LangSmith is strong when LangChain/LangGraph tracing, datasets, experiments, online evaluation, and team UI are already used. Its agent guidance explicitly covers final response, trajectory, and single-step evaluation. OpenEvals provides Python/TypeScript evaluators for structured outputs, RAG, code, trajectory matching, trajectory judges, and multi-turn simulation. Its strict/unordered/subset/superset trajectory modes are useful when the allowed path flexibility is explicit.

### Braintrust

Braintrust centers on portable data-task-scorer experiments, immutable comparisons, repeated trials, CI/CD, production scorers, and feedback-to-dataset workflows. It offers built-in autoevals, custom code, and LLM-as-judge scorers. It is a strong vendor-neutral managed choice for teams that want experiments and observability without adopting a specific agent framework.

### DeepEval

DeepEval is a Python/pytest-style open-source framework. It exposes agentic metrics such as task completion, tool correctness, argument correctness, step efficiency, plan quality/adherence, RAG metrics, multi-turn metrics, and MCP metrics. It is convenient for code-first teams, but prebuilt LLM metrics still require project-specific validation and should not replace deterministic outcome checks.

### Promptfoo

Promptfoo is strong for local YAML/CLI prompt and model matrices, CI assertions, and adversarial red teaming. Its agent red-team workflow can consume OpenTelemetry traces containing tool executions and guardrail decisions. Use it as the security/adversarial layer or lightweight matrix runner; use a stateful harness for deep environment outcome evaluation.

### Ragas

Ragas provides ready-made RAG and agent metrics, including tool-call accuracy and agent-goal measures. It accelerates experiments, especially for retrieval/generation decomposition. Supplement LLM-derived metrics with labeled evidence, classic IR metrics, access-control tests, freshness checks, and environment outcomes.

### Phoenix/OpenInference and MLflow GenAI

Phoenix is a strong open-source/self-hosted choice for OpenTelemetry/OpenInference traces, human annotations, datasets, experiments, and code/model evaluators. It supports RAG and tool-calling analysis and can integrate external evaluators. MLflow GenAI is attractive where MLflow is already the system of record; it evaluates stored production traces and supports built-in/custom scorers.

### Custom pytest plus OpenTelemetry

For maximum control and low lock-in, keep JSONL fixtures, typed Python graders, pytest, sandboxed integration environments, and OpenTelemetry traces as the base layer. Add a managed platform as an adapter for visualization, large experiments, annotation, and online scoring.

## 7. Benchmark lessons

Public benchmarks are useful for model/harness screening, not product release decisions.

- Tau-bench evaluates policy-following tool-agent-user interaction in retail and airline environments and emphasizes repeated-run reliability.
- BrowseComp tests deep information retrieval; Anthropic's 2026 investigation documents leaked answer sources and a higher unintended-solution rate in its multi-agent configuration, showing contamination and eval awareness risk.
- SWE-bench, Terminal-Bench, OSWorld, WebArena, and similar environment benchmarks demonstrate the value of executable outcomes, but harness details and environment health materially affect scores.
- MultiAgentBench evaluates collaboration and competition, but a product should additionally measure handoffs, state consistency, duplicated work, synthesis loss, and quality-per-cost against a single-agent baseline.
- RAG research in 2025 emphasizes measuring retrieval and generation separately and studying configuration stability, scale, and realistic evidence annotations.

Anthropic notes that an apparent zero pass rate across many trials often indicates a broken task or grader. It also warns that saturated evals become regression tests rather than improvement signals. The practical response is to audit tasks, retain stable regressions, and continuously introduce harder unsaturated capability cases.
